ChatConvert

LLM architecture & technical guide

How the AI sales & support agent works across the whole process — for a public, embedded Shopify app. Use the menu on the left to jump to any topic, or the arrows (top-right / keyboard ← →).

Two levels are covered: the architecture (the pieces and how data flows in and out) and the technical flow (every runtime step as code — search, DB, RAG, chat history).

Core principle: the LLM is only the voice. A pipeline around it decides what the shopper needs, retrieves the right data (catalog / knowledge / live Shopify facts), and constrains the model so answers are accurate and safe. The LLM never touches the database directly. Everything is multi-tenant — scoped to one shop.

Code is illustrative pseudo-code for a Remix/Node backend + Postgres (pgvector). Tags: LLM model call · DB Postgres/pgvector · Shopify live API · code backend logic.

Architecture

System architecture — the pieces

Three zones: the two Shopify surfaces (storefront widget for shoppers, admin app for the merchant), your multi-tenant backend (API, the agent pipeline, cache, webhook handlers, billing, logging), and the three dependencies it calls — the LLM provider, the vector DB, and the Shopify APIs. Every arrow is labelled with the operation that flows across it. All state is scoped by shop_id.

Architecture

Data ingestion — getting the store's knowledge AI-ready

Ingestion runs in the background — on install, on Shopify webhooks, and on a schedule. Each source type follows its own little pipeline to become searchable vectors (or plain rules). Every arrow names the operation that runs between the boxes.

1 · Catalog sync

On products/create|update|delete webhooks, normalize the product, embed title + description, and upsert the row + its embedding. A scheduled reconcile catches any missed webhooks. Stock/price are stored but re-checked live at answer time; text changes trigger re-embedding so meaning search stays accurate.

2 · Knowledge ingestion

The merchant connects a source — a policy page, URL, PDF, CSV, or manual text. You fetch it (with SSRF protection on URLs), strip HTML to clean text, chunk it into ~500–1500-character pieces with a small overlap (so a fact spanning a boundary isn't lost), embed each chunk, and store it with a reference back to its source (for citations).

3 · Curated answers & config

Curated questions (+ synonyms) are embedded on save so they can be matched by meaning. Persona and guardrails are stored as plain rows and loaded as rules — no embedding needed.

Embeddings are computed once here and reused forever until the row changes — the runtime never re-embeds your catalog, only the shopper's message.

Steps 0–2 — request, entry, guardrail

0

The widget sends the messagecode

The widget POSTs to your backend with a shopId and a per-session sessionId (how messages tie into one conversation). The widget never calls OpenAI — keys stay server-side.

POST /apps/chatconvert/message
{ "shopId": "shop_123", "sessionId": "sess_abc", "message": "warm gloves under $30" }
1

Backend entry — auth, tenant, rate-limitcode

Authenticate the tenant and pin every later query to that shopId; rate-limit per session/shop; bound the input; load the shop's cached config and the conversation (for history).

export async function action({ request }) {
  const { shopId, sessionId, message } = await request.json();
  await verifyShopSession(shopId, request);        // tenant auth
  if (!rateLimiter.allow(shopId, sessionId)) return tooMany();
  const text  = message.slice(0, 2000).trim();
  const cfg   = await loadShopConfig(shopId);       // persona + guardrails, cached
  const convo = await getOrCreateConversation(shopId, sessionId);
}
2

Guardrail — decide by meaning (before the router)keywordmoderationembeddings

Shoppers rarely type the banned word, so this decides by meaning — using three cheap checks, none of which is the chat LLM: a keyword pre-check; OpenAI's free moderation model for universal-unsafe content (sexual / hate / violence / self-harm); and an embedding similarity check against the merchant's own banned topics (politics, competitor pricing), reusing the message embedding. If any fires → fallback, and the router never runs.

const mod = await moderation(text);                  // FREE model · universal unsafe
const bannedScore = maxCosine(qVec, bannedTopicVecs);   // store-specific, by meaning
if (keywordHit(text) || mod.flagged || bannedScore >= 0.35)
  return reply(cfg.guardrails.fallbackMessage);        // no chat-LLM call at all

These cheap checks catch the obvious cases (universal-unsafe + close meaning matches). But they miss abstract topics — e.g. "which medicine is good for fever" is medical advice, yet has no matching keyword and may score below the embedding threshold. Those nuanced cases are caught by the router's blocked flag (step 4) — the LLM understands the meaning. So the guardrail is layered: cheap checks here + the router LLM as the reliable backstop (still one LLM call).

Steps 3–4 — curated match & router

3

Curated match — by meaning (embeddings + LLM confirm)embedDB

Shoppers rarely type the curated question verbatim, so match by meaning: embed the message, find the closest curated question with pgvector, and decide by score band — high → use it (no generation); borderline → one cheap LLM yes/no confirm to avoid a wrong match; low → skip. No moderation here (that's a safety tool, not a matcher). 1 - (embedding <=> qVec) turns cosine distance into a similarity score.

const [top] = await sql`
  SELECT question, product_ids, talking_points,
         1 - (embedding <=> ${qVec}) AS score
  FROM curated_answer WHERE shop_id = ${shopId}
  ORDER BY embedding <=> ${qVec} LIMIT 1`;
if (top.score >= 0.80)  return curatedReply(top);           // confident → no LLM
if (top.score >= 0.65 && await llmConfirm(text, top.question))
  return curatedReply(top);                           // borderline → LLM confirms
// else: skip curated, continue the pipeline
4

Intent router — one small LLM callLLM

A cheap, fast model call returns structured JSON — the lane plus hints (price, keywords), a blocked flag for banned topics, and an off_topic flag for out-of-scope requests. It does three jobs in one call: classify intent, catch nuanced banned topics the cheap checks missed (e.g. "which medicine for fever" = medical advice), and flag anything outside the store's domain. If blocked → fallback; if off_topic → polite redirect.

const routed = await chat({
  model: "gpt-4o-mini", temperature: 0,
  response_format: { type: "json_object" },
  messages: [ { role:"system", content: ROUTER_PROMPT + BANNED_TOPICS + STORE_SCOPE },
              ...recentHistory,      // summary + last 10
              { role:"user", content: text } ]
});
// → { "intent":"question", "blocked":true, "blocked_reason":"medical advice",
//     "off_topic":false, "off_topic_reason":"" }
if (routed.blocked)   return reply(cfg.guardrails.fallbackMessage);   // banned topic
if (routed.off_topic) return reply(persona.offTopicMessage);          // out of scope → redirect

Off-topic vs blocked: a grocery store asked about cars isn't unsafe — just out of scope. The router knows the store's scope (from persona) and sets off_topic, so you politely redirect ("I can only help with our store…") instead of the fallback. Greetings and small talk are not off-topic.

After the intent — what each lane does

The router only labelled the message. Now your code branches to the matching lane. Each lane fetches only the facts that answer needs; the LLM then phrases the reply from those facts (step 6). Here is every lane — including human handover.

if (routed.blocked)              return fallback();                            // guardrail
if (routed.intent === "buy")     context.products = await hybridProductSearch(shopId, text, routed);
if (routed.intent === "support") context.snippets = await ragKnowledge(shopId, text, cfg);
if (routed.intent === "order")   context.order    = await shopifyOrderStatus(shopId, routed);
if (routed.intent === "chat")    context = {};                                 // no lookup
if (needsHuman(routed, convo))   return handover(shopId, convo, text);          // escalate

BUY lane — hybrid product searchDB

Keyword + vector search, filtered by price/stock, merged into a shortlist (the "allow-list"). If nothing fits but there's a budget → show the cheapest in-budget items; if nothing at all → ask a clarifying question instead of guessing.

-- keyword + hard filters
SELECT id,title,price FROM products
WHERE shop_id=$1 AND stock>0 AND ($2 IS NULL OR price<=$2)
  AND to_tsvector(title||' '||description) @@ plainto_tsquery($3);
-- vector (meaning), same filters
SELECT id,title,price, 1-(embedding <=> $q) AS score FROM products
WHERE shop_id=$1 AND stock>0 AND ($2 IS NULL OR price<=$2)
ORDER BY embedding <=> $q LIMIT 8;
// merge + dedupe; keep vector rows with score ≥ 0.30 → the candidate shortlist

SUPPORT lane — RAG over knowledgeDB

Vector search pulls the few closest knowledge chunks. If nothing relevant is found → decline (don't guess). The LLM answers only from these snippets.

SELECT topic, body, 1-(embedding <=> $q) AS score
FROM knowledge WHERE shop_id=$1 ORDER BY embedding <=> $q LIMIT 3;

ORDER / live-data lane — Shopify toolShopify

Facts that change (stock, price, order status) are read live from Shopify, never the vector index.

const order = await shopify.graphql(shopId, `query($q:String!){
  orders(first:1, query:$q){ nodes{ displayFulfillmentStatus
    fulfillments{ trackingInfo{ url } estimatedDeliveryAt } } } }`, { q:"name:#1234" });

CHAT lane — small talk

No lookup — the LLM gives one short, on-persona reply (optionally nudging toward shopping).

HUMAN HANDOVER — the safety valvecode

When it triggers: the shopper asks for a person, the agent has failed a few turns in a row, it's a sensitive case (complaint, damaged order, refund dispute), or a merchant rule requires it. What happens: post a calm handover message, capture the shopper's email, open a ticket in the merchant's inbox, and pass the same conversation to a human — the agent then stays quiet until it's resolved. A defined exit, not a dead end.

async function handover(shopId, convo, text){
  const email = convo.email ?? await askForEmail();       // so the team can follow up
  await createInboxTicket(shopId, convo, { reason: text }); // route to a human
  await notifyMerchant(shopId, convo);                     // email / Slack
  convo.mode = "human";                                  // agent goes quiet on this chat
  return reply("Let me connect you with our team — they'll reply here shortly.");
}

The runnable demo implements buy / support / chat / blocked. Order/live-data and handover need the live Shopify API + a merchant inbox — shown here as the production design.

Generation — grounded + streamingLLM

Build the prompt from three parts: system (persona + grounding rules), recent history (coherence), and a user message with the retrieved data + question. The model can only use what it's given, so it can't invent products or facts. Stream tokens to the widget.

const stream = await chat({ model:"gpt-4o-mini", stream:true, messages: [
  { role:"system", content: systemPrompt(cfg.persona) + GROUNDING_RULES },

Knowledge: ${JSON.stringify(context.snippets ?? [])}

for await (const token of stream) sse.send(token);

Tool-calling variant: give the model tools (search_products, get_order_status…); it decides which to call, you execute and return results, it loops until it answers — handling mixed intents in one exchange.

7

Cards, stream & logcode

Cards are built from DB rows (real price/image), the reply streams out, and both messages are persisted (that's what makes history work next turn) with an analytics event.

const cards = (context.products ?? []).map(p => ({ title:p.title, price:p.price, image:p.image_url, url:`/products/${p.handle}` }));
await logTurn(convo, { role:"assistant", text: reply, cards, intent: routed.intent });
Deep dive

How vector (meaning) search works

An embedding is a fixed-length list of numbers (1536 for text-embedding-3-small) that represents text's meaning as a point in space. Similar meaning → nearby points, even with no shared words — "keep my hands warm" sits near "insulated wool gloves".

Measuring closeness — cosine similarity: cos = (A·B)/(|A||B|). 1.0 = same meaning, ~0 = unrelated. pgvector operators: <=> cosine distance (we use this), <-> Euclidean, <#> inner product.

SELECT id, title, price, 1 - (embedding <=> $q) AS score
FROM products WHERE shop_id = $shop AND stock > 0
ORDER BY embedding <=> $q      -- nearest neighbours first
LIMIT 8;

Staying fast — the index. Comparing to every row is fine for a few thousand products; for large catalogs add an approximate nearest-neighbour (ANN) index:

  • HNSW (recommended) — a layered graph; search hops to the query's neighbourhood. Fast, high recall, more memory. CREATE INDEX ON products USING hnsw (embedding vector_cosine_ops);
  • IVFFlat — clusters vectors into lists; scans only the nearest few. Lighter, needs a tuned lists count.

"Approximate" may miss a marginal match occasionally in exchange for big speed-ups — the right trade at scale. Normalise vectors on write for consistent cosine behaviour.

Deep dive

How hybrid search works (and why)

Keyword search (Postgres tsvector/BM25) is exact — great for specific tokens and hard filters (price ≤ 30, in stock, type) — but blind to meaning. Vector search is the opposite. Hybrid runs both and combines them: precise filtering and semantic recall.

const [kw, vec] = await Promise.all([   // run both in parallel
  keywordQuery(shopId, routed),
  vectorQuery(shopId, await embed(text), routed)
]);
const merged = dedupeById([...kw, ...vec.filter(r => r.score >= 0.30)]).slice(0,8);

Combining rankings. Simplest is union + de-dupe. More principled: Reciprocal Rank Fusion (RRF) — score each item by Σ 1/(k + rank_in_each_list) and sort by that; it blends a keyword ranking and a vector ranking without needing their scores on the same scale. Hard filters (price/stock) are always SQL WHERE, never left to similarity. Optionally add a reranker (cross-encoder) on the merged top-N for the best ordering once traffic justifies it.

Fallbacks that feel good: nothing matched but a price cap exists → return cheapest in-budget ("browse"); genuinely nothing → ask a clarifying question rather than guess.

Deep dive

How the DB calls work effectively

  • Always scope by shop_id — first column of composite indexes. Tenant isolation and a smaller working set per shop.
  • Index each access path — HNSW on embedding, GIN on to_tsvector(...), btree on (shop_id, price)/(shop_id, stock). Without these, searches do full scans.
  • Parameterised / prepared statements — pass values as parameters (never string-concat): prevents SQL injection, lets Postgres cache plans.
  • Connection pooling — put PgBouncer (or your platform's pooler) in front so serverless handlers reuse connections.
  • Select only what you need and LIMIT results — don't pull full descriptions or embeddings back to the app.
  • Cache the expensive bits — product/knowledge embeddings computed once at ingestion; cache config; optionally cache the query embedding for repeated questions.
  • Batch on ingestion — embed many rows per call, upsert in batches, so a catalog sync is a few round-trips not thousands.
  • Scale reads with a read replica; searches are read-only.
Deep dive

How chat history is handled in a session

A session is one shopper's ongoing conversation, tied by the sessionId the widget sends each message. History lets the agent resolve "the second one", remember a budget, and avoid repeating itself.

Storage. Each turn is a row in message, linked to a conversation (one per session), created on the first message and reused after.

conversation(id, shop_id, session_id, started_at, outcome)
message(id, conversation_id, role, content, product_cards, intent, created_at)

The context window. The model can accept a lot (gpt-4o-mini ≈128k tokens), but you never send the whole conversation — for cost, latency, and focus. You send a recent window + a rolling summary.

Recent window — the last 10 messages, sent verbatim:

const recent = history.slice(-10);            // last 10 messages, verbatim

Rolling summary for long chats. Once the conversation grows past the window, the older turns are compressed into a short, cached summary (one cheap LLM call, refreshed every few turns), and you send summary + the last 10 — never the whole thread:

const recent  = history.slice(-10);
const older   = history.slice(0, -10);
if (older.length && needsRefresh) summary = await summarize(older);   // cached, refreshed every few turns
const context = summary
  ? [{ role:"system", content:"Earlier conversation summary: "+summary }, ...recent]
  : recent;                                    // → sent to the router + generation

Don't over-feed retrieval: history helps the router and generation understand intent and tone, but product/knowledge search is driven mainly by the current message.

Implemented in chatconvert_ui.py: RECENT_LIMIT = 10; re-summarize every SUMMARY_EVERY = 4 older messages; summary cached on the conversation. Prompt in prompts.json → summary_system.

Deep dive

How RAG works over the knowledge base

RAG (Retrieve-Augmented Generation) answers support questions from the merchant's own content, not the model's general knowledge. Two phases:

Ingestion (once per source)

Fetch the source (SSRF-guarded for URLs), strip markup to clean text, chunk into ~500–1500-char pieces with overlap, embed each, store with a reference back to its source. Smaller chunks = more precise retrieval; larger = more context per chunk.

Retrieval & grounding (per question)

const rows = await sql`
  SELECT topic, body, source_id, 1-(embedding <=> ${q}) AS score
  FROM knowledge WHERE shop_id=${shopId}
  ORDER BY embedding <=> ${q} LIMIT 3`;
if (answerOnlyFromKnowledge && (!rows.length || rows[0].score < minScore))
  return { decline: true };            // nothing relevant → don't guess

The generation prompt is then: "Answer using ONLY the store info below … [the 3 chunks] … Question: …". That's the whole trick — retrieval decides the facts, the model only phrases them, and a score threshold decides when to decline. Keep the source_id to show a citation.

Production

What makes it robust

  • Grounding, not guessing. The LLM only receives the retrieved data — it can't invent a product, price or policy.
  • Live data via tools, not the index — stock, price, order status read from Shopify at answer time, never stale.
  • Safety first. Guardrails and curated answers run before the LLM, so banned topics and top questions don't depend on the model.
  • Multi-tenant isolation — every query scoped by shop_id, set from the authenticated session, not the request body.
  • Streaming — tokens relayed to the widget so replies appear instantly.
  • Graceful escalation — hand over to a human (inbox/email) when the agent can't help.
  • Caching & cost control — reuse embeddings, prompt caching, per-plan usage caps.
  • Feedback loop — log + score every turn (outcomes + LLM-judge) to keep improving prompts, knowledge and curated answers.
  • Compliance — GDPR webhooks, retention windows, PII care — required for a public Shopify app.
Production

Topics that are easy to miss

Personalization

Use browsing behaviour, cart contents and purchase history as extra signals into retrieval and the prompt, so recommendations and upsells fit context.

Multi-language

Detect the shopper's language; embeddings are multilingual; instruct the model to reply in their language; keep merchant strings translatable and format prices by locale.

Prompt-injection & input security

Shopper text and ingested content are untrusted. Keep system rules authoritative and separate from user text; never let the model set prices/discounts (those come from DB/tools); treat tool output as data, not instructions. The allow-list grounding already limits the blast radius.

Evaluation & testing

Before shipping prompt/model changes, run a golden set of real questions with an LLM-as-judge plus human checks to catch regressions.

Catalog freshness

Re-embed on products/update; remove on delete; scheduled reconcile for missed webhooks.

Observability

Trace every call (tokens, latency, cost, retrieved ids); dashboard p50/p99, error rate, cost per conversation, chat-to-sale.

Latency & cost, provider resilience, widget UX, outcome/lead capture

Parallelise calls; small model for routing; timeouts + retries + a fallback model/handover; typing indicators, suggested prompts, add-to-cart; classify outcomes and capture emails on a miss.

Summary

The call sequence for one message

#StepWhat runs
1Backend entrycode (auth, rate-limit, config, conversation)
2Guardrailcode — may return early
3Curated match1 embedding + 1 pgvector query — may return early (no LLM)
4Router1 LLM call (JSON), with recent history
5Retrieve1 embedding + 1–2 SQL queries, or a Shopify API call
6Generate1 LLM call, streamed, with history (or a tool-calling loop)
7Cards + logcode (cards from DB rows, persist messages + analytics)

A normal turn ≈ 2 LLM calls + 1–2 embedding calls + a few DB/Shopify queries.

The seam that keeps it robust: steps 2–5 decide what and fetch the facts; step 6 only phrases the answer from those facts, with history for coherence. Control what enters the step-6 prompt and the model cannot hallucinate — that's grounding, enforced in code.
